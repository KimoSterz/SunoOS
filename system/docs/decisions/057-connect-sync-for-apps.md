# ADR-057: Connect Sync for apps

- **Status:** Accepted
- **Date:** 2026-11-24
- **Owner:** Project Luma
- **Reviewed:** adversarially on 2026-11-24 before building (verdict: sound with changes); its three High and six Medium findings are folded into sections 1, 2, 3, 5, 7 and 9.
- **Review basis:** `luma-connect-sync` at 41719c8a (`engine.py`, `crypto.py`, `appdata.py`, `service.py`); wire format 2 (`docs/operations/connect-sync-wire.md`); the Hub module `deploy/hub/connect-sync/` (website repo, 6e231bb); `luma_installer.app_identity` and `app_permissions` (ADR-052 step 3); xdg-desktop-portal 1.22.1 with Luma's patches 0001–0005; OpenLator (nmcmil/OpenLator b977218) as the first adopter; CloudKit, CKSyncEngine, Android Auto Backup and Steam Cloud as prior art
- **Revisit trigger:** a request to share a zone between two accounts; an app that needs server-side queries over its data; the peer lane (`luma-sync-net`) shipping; the Android companion; a paid tier being priced; more than 1,000 apps using the API
- **Extends:** ADR-054 §5 and §5a (the Connect Sync API), which this ADR makes concrete and tightens. Where they differ, this ADR wins. ADR-052 (app identity, permissions), ADR-051 (keys)

## User problem

Someone plays a game on the living-room TV, saves, and picks the same game up on the laptop in a bag, on a phone on the train, or on a tablet in bed. The save is there, and so is the library: the games, the collections, what was played last. Nobody set anything up besides signing in to Luma Connect once. A recipe app, a notes app or a reading app wants the same thing for its own data.

Today an app gets this only by running its own server and accounts, or by Luma copying its whole data folder when it is closed (ADR-054 §4), which cannot merge two devices' changes and moves far more bytes than the app needs.

The API must be safe against the app that uses it. An app is untrusted code. It must not be able to read or damage another app's data, learn who the person is, reach another person, use Luma's servers as free storage or a network tunnel, or run up the person's bandwidth.

## Constraints

- Apps never hold a key, a token, a Hub address, a device address or a path outside their own sandbox.
- An app's identity comes from its sandbox and its signed origin, never from anything the app says.
- The Hub sees ciphertext, sizes, times and opaque identifiers only. It may not learn which app a zone belongs to, or which person uses which app.
- No app syncs until Luma has approved it in the Hub (section 10). Luma can see every approved app's usage in detail and revoke it at any time.
- Lightweight: no new server, no per-app server work, no query engine. Bytes between the person's own devices go device to device where they can.
- Works on every device class (computer, handheld, TV) and both architectures, from one client library.
- Nothing blocks an app waiting for an answer. With Sync off, no account, or permission not yet given, calls succeed locally and queue.

## Decision

### 1. App identity and zone ownership

1. **Who is calling.** The portal frontend (section 3) names the caller from its sandbox, the same way it does for every other portal (`XdpAppInfo`), and passes the app ID, the kind and the caller's pidfd to the sync service. The service checks the pidfd again itself: the process is alive before and after it reads `/proc`, and its `/.flatpak-info` names the same app.
   - *Flatpak* is supported from Phase 1.
   - *ADR-052 applications* talk to the bus through `xdg-dbus-proxy`, which their launcher starts as an unlabelled host process, so the portal can name them only by their launcher's scope name. A scope name is chosen by whoever starts the scope, so the Sync API refuses that. ADR-052 applications get the API when the launcher starts the proxy in the application's own SELinux level (Phase 2); the service then names them by level only.
   - Callers the portal names as the host, and any empty or invalid app ID, are refused outright: no mirror, no outbox, no local data.
2. **Who publishes it.** The *owner* is resolved on the device from the installation, never from the app:
   - *Flatpak:* the service reads the commit the instance runs (`app-commit`, in the installation its `app-path` lies in), checks that the object hashes to that checksum and is bound to the app (`ostree.ref-binding`, else `xa.metadata`), and verifies the commit's OpenPGP signatures against the publisher keys the signed app registry approved for that app ID (section 10.3). A valid signature by an approved primary key, or by a signing subkey bound to it, makes the app that registry entry's owner: `flatpak:<first 32 hex of SHA-256(lp(remote URL, primary-key fingerprints…))>`, computed by the Hub from what the publisher registered. The local remote configuration (its URL, `gpg-verify`, its keyring) is never proof: it is text an app with home access can write. A commit signed only by a key no approved entry lists is `not-approved` (its writes wait under that key); a commit with no valid signature (an unsigned remote, `gpg-verify=false`, a local build, a keyless bundle) is `unverified`. Subkey fingerprints never enter the owner, so a publisher can rotate signing subkeys without orphaning its zones. (ADR-054 §4's app-folder owner still hashes the remote's keyring as configured; aligning it is tracked separately.)
   - *The trust boundary:* the owner is as good as the installation's files. A system installation (`/var/lib/flatpak`) can't be written by apps. A user installation (`~/.local/share/flatpak`) can be written by an app that has write access to the home folder (`--filesystem=home` or `host`); such an app can already read every other app's data folder, so it is inside the boundary, for this API as for ADR-054 §4. (Flatpak hides `~/.local/share/flatpak` from `--filesystem=home` unless `xdg-data/flatpak` is granted, and `--talk-name=org.freedesktop.Flatpak` is a full host escape; the "All files" level in Settings and Depot should key on those grants and `host`.)
   - *ADR-052 store application (Phase 2):* `depot:<publisher key fingerprint>` from the signed Depot record, checked against its signature when it is read, or `userland:<name>:<package>` for a tree whose package came from that distribution's own signed repository with no added repository. The record and the level map live where apps can't write (ADR-052's protected list).
   - *Android (later):* package name and signing certificate digest.
   - *Anything else* (an unsigned remote, a sideload, a local build): no owner. `GetStatus` answers `unverified` and every other call is refused; nothing is stored, so nothing unverified can later move into a verified zone. Connect developer mode (later) gives such apps a `dev:` owner that syncs only between devices that all have developer mode on.
3. **Zones.** An app names its zones with short labels (`saves`, `library`). The service names the zone `api:` followed by the hex of lp(owner, app, label), so the name is unambiguous whatever the parts contain, and the Hub knows it only as the keyed hash of that string (wire format 2, "Zone id"). The `api:` prefix keeps every app zone apart from system zones (`apps`, `keychain`, `appdata:…`, `portal:…`). An app can't name a zone of another app or of the system: it supplies only the label.
4. **Same app ID, different publisher.** An impostor that installs the same app ID from another remote gets another owner, so another zone, and sees nothing of the real app's data. On the device, an app's local mirror and cache are keyed by owner and app, so the impostor gets an empty one.
5. **The app directory.** A device that doesn't have an app can't compute its zone IDs. So every device keeps one encrypted record per app in the system zone `api-directory`: owner, app, the app's verified name, its labels and tag, whether the person turned it off, and which devices have it installed, with times. A device fetches only the zones of apps installed on it, and uses the directory to show, meter, turn off and delete the zones of apps it doesn't have.
6. **Sharing between apps.** Not in this ADR. Two apps of one publisher may later share a zone through a `sync.group` in the signed store record.
7. **Publisher changes.** Moving an app to a new publisher key needs a continuity statement signed by both keys (later). Until then, a new key is a new owner, and the old zones stay readable to the old owner.

### 2. Keys and what the Hub sees

1. **Zone keys.** Each app zone has its own random 256-bit key and key generation, wrapped under the account sync key as every zone key is (wire format 2, "Zone key wrap"). The wrap's associated data binds the account, the zone ID, the generation and the epoch, and the zone ID is a keyed hash of the verified owner, app and label. A key wrapped for one app's zone therefore cannot be unwrapped as another's, and the Hub can't move a key, record or blob between zones. Records and blobs use the zone's key with XChaCha20-Poly1305, as in ADR-054.
2. **No app ever holds a key.** Records reach the app as plaintext over its own D-Bus connection. Assets reach it as read-only file descriptors. The service holds every key.
3. **App tag.** For quotas, the Hub must group an app's zones without learning the app. Each app zone is created with `owner` = the app's *tag*: `t` and the first 16 bytes, hex, of mac(HKDF(names, `luma-sync-app-tag-v1`), account, owner, app). The tag is the same on every device of an account and different in every account, so the Hub can't tell which app it is or link two accounts that use the same app. This replaces ADR-054 §1.8 "the owning app ID of third-party zones".
4. **Sizes and timing.** App records are zlib-compressed and then padded with zeros to the Padmé length of at least 1 KiB before they are sealed, as blobs are; readers ignore bytes after the zlib stream, so wire format 2 doesn't change. App writes leave in the service's own sync cycle, coalesced per record, never one request per call.
5. **The Hub sees:** zone IDs, app tags, padded record and blob sizes, counts, times and the writing device. Over time it can still see that some app is used on a device, and roughly how much it stores. **It can't see:** app IDs, publishers, labels, record names, values, asset names or contents.
6. **Revocation.** Removing a device makes a new account key and new zone key generations for every zone (ADR-054 §1.7), app zones included. Nothing about app zones changes the rekey.

### 3. API surface

1. **Portal.** `org.projectluma.portal.Sync` on `/org/freedesktop/portal/desktop`, served by xdg-desktop-portal (patch 0006). Every Flatpak can already reach the portal bus name; ADR-052 applications reach it through their bus proxy. The frontend is a thin forwarder: GDBus checks each call against the interface's introspection, and the frontend adds the caller's identity and passes the call, with any file descriptors, to the implementation, `org.projectluma.impl.portal.Sync` at `/org/projectluma/ConnectSync1/Apps` on `org.projectluma.ConnectSync1` (luma-connect-syncd). The implementation answers only the current owner of `org.freedesktop.portal.Desktop`, and only when that peer runs in `xdg-desktop-portal.service`, so an app that reaches the session bus directly can't call it with an identity of its choosing. The management interface `org.projectluma.ConnectSync1` keeps refusing every sandboxed caller.
2. **Signals reach only the app.** `Changed`, `AssetChanged` and `StatusChanged` are sent by the frontend to the connections of the app they belong to, after the app called `Subscribe`, never broadcast. Any `Subscribe` call also subscribes the app to `StatusChanged`, whatever zones it names.
3. **Model.** Zones, records, assets and leases. No queries, no server code, no REST.
   - A **record** is a name (UTF-8, at most 255 bytes) and an opaque value (at most 256 KiB), with a version.
   - An **asset** belongs to a record under a name (at most 32 per record). *Inline* assets (at most 64 MiB each) are resident: kept on the Hub within the app's quota and fetched with the record. *On-demand* assets (at most 16 GB each) are device-held: metadata syncs everywhere, bytes move device to device when a device asks or pins (section 6).
   - A **lease** marks a record as in use on one device (`playing this game`), for at most an hour, renewable. It is advisory and never blocks.
4. **Calls** (all take a zone label; all answer at once; writes are durable before they return):
   - `GetStatus()`: `available`, `off` (Sync turned off), `no-account`, `not-allowed` (the person turned the app off), `offered` (waiting for the person's answer), `unverified` (no owner), `not-approved` (Luma hasn't approved the app, or approved another publisher's build), `suspended` (Luma paused the approval), `revoked` (Luma withdrew it); the app's usage and limits; this device's class; this device's handle for this app (the same handle `FetchChanges`, leases and siblings use). The client library adds a seventh state, `unavailable`, when there is no portal (item 7); the enum carries all ten. When several apply, the first wins: `revoked`, `suspended`, `unverified`, `unavailable`, `not-approved` (for the zone's label or the whole app), `no-account`, `off`, `not-allowed`, `offered`, `available`. A zone label Luma hasn't approved for the app gives that zone `not-approved`, with exactly the app-wide behaviour (local calls work, writes queue). Under `revoked` and `suspended`, writes answer `local`: saved on this device only, never queued and never synced; under `not-approved` they still queue, within the outbox cap, since approval may come later.
   - `Subscribe(zones)`: start receiving `Changed(zone)` for those zones.
   - `Save(zone, records, options)`: each record is (name, value, base version). Answers saved, kept-both, conflict (with the current value), too-many-siblings, queued or local. `on_conflict` is `keep-both` (default) or `fail`. A queued write whose base is already stale against the mirror answers kept-both, with the record marked queued.
   - `Delete(zone, names and base versions)`.
   - `FetchChanges(zone, token)`: records changed since the token, with the next token, from the service's local mirror. The token is the app's: the service never advances it, so an app that saves the next token only after applying the records never misses one (crash-safe). Records come with each record's version, writer device (a handle stable for this app only, the device's class and the name the person gave it), time, asset names and siblings.
   - `Get(zone, name)`, `List(zone, after, limit)`: local reads.
   - `PutAsset(zone, record, name, fd, base version, options)`: the descriptor must be a sealed memfd or a regular file outside FUSE. The service copies it into its own spool, with a size cap and a deadline, and hashes and encrypts only the copy; it never opens a path the app names. `options.on_demand` makes it an on-demand asset.
   - `RemoveAsset(zone, record, name, base version)`: drops one asset. Its bytes stop counting against the quota once the removal reaches the Hub. A stale base is a conflict like any write.
   - `OpenAsset(zone, record, name, version)`: `version` is optional and defaults to the current one; it may name any live sibling, so an app can show the other device's save or thumbnail before the person chooses; an unknown or resolved version answers `gone`. The answer is a read-only descriptor of a private copy of the bytes, never of the service's own files: a memfd sealed against writes and growth up to 4 MiB, else an unnamed file on the store's disk (a reflink where the filesystem has them). Copies count against the app's open-copy cap (1 GiB and 64 copies; one copy always fits) for as long as any process in any of the app's cgroups (every instance and sub-sandbox) holds a descriptor or a mapping of them; after two scans in a row find none, the service drops its own reference, which frees the space unless something it can't see, such as a process outside the app's cgroups that the app handed the descriptor to, still holds the copy. Copies are never truncated, so such a holder still reads every byte. The hourly open budget lets an asset larger than its burst through when the budget is full, charged as debt. The answer may instead be `not-here` with where the bytes are ("On Dell XPS 14 · offline").
   - `RequestAsset`, `PinAsset`, `EvictAsset` for on-demand assets; `AssetChanged` reports progress.
   - `Lease(zone, record, seconds, take_over)`, `Release(zone, record)`: answer who holds it and until when, with `mine` set when the holder is this device. Siblings carry `mine` too. `GetLease(zone, record)` reads the lease without taking it (`active` false and `until` 0 when there is none), so an app can show "Paused on Living room TV" (§7.3).
   - `ResolveSiblings(zone, record, keep)`: the person chose a version. Answers like a write: saved, queued (Sync can't send it now), local (revoked or suspended), or conflict or too-many-siblings when a new version raced it.
   - `DeleteZone(zone)`: the app's own data, on every device.
5. **Conflicts keep both.** A write whose base version is stale, from a device that was offline or from the outbox after the app quit, never overwrites. With `keep-both`, the newer write (by hybrid logical clock) becomes current and the other becomes a sibling labelled with its device and time ("from Living room TV, 21:04"), at most four per record, until the app calls `ResolveSiblings`. With `fail`, the app gets the current value and merges.
   - **`fail` applies only to a write answered while the app waits.** A write the service answers `queued` has no one to fail to, so it always resolves as `keep-both` when the outbox drains, and the `queued` answer says so.
   - **A fifth version never drops data.** A direct `Save` or `RemoveAsset` that would make a fifth version answers `too-many-siblings` with the current value and its siblings. An outbox write that would do so is held on the device, `GetStatus` and `FetchChanges` report the record as `held`, and `Changed` fires. It leaves once the app calls `ResolveSiblings`.
   - **A stale delete never wins.** A `Delete` whose base is older than an edit from another device is dropped and the edit stays current. A direct `Delete` answers `conflict` with the current value; one from the outbox appears in `FetchChanges` as `delete-dropped`, so the app can delete again if it still means to.
   - **Assets follow the record rules.** A direct `PutAsset` on a stale base answers `conflict`; one from the outbox resolves `keep-both`, as for `Save`.
   - **A delete on the current base clears the siblings too.** It is a decision over every version of the record.
   - **Resolving keeps the chosen content under a new version.** `ResolveSiblings` writes the kept version as a new version id with its original writer, time and content, plus `resolved_by` (the resolving device), so devices that still hold an older base conflict correctly.
   - **Sibling times come from the hybrid logical clock,** the same time that orders them, never the writer's raw wall clock. The Hub clamps a write whose clock runs more than 60 s ahead of its receive time to that receive time, so a skewed device can't label a sibling in the future.
   - **`Changed` is for what the app didn't just see.** It fires for remote changes and for the outcome of the app's own queued writes (saved, held, `delete-dropped`), never for a write answered while the app waited. It carries no records: the app fetches with its token. The library's `siblings` signal follows the same rule.
6. **Offline outbox.** Writes go to a durable per-app outbox and leave when Sync can send them. An app can write and quit. The outbox counts against the app's quota.
7. **Client library.** `LumaSyncStore` in LumaUI (`luma-sync.h`, GObject, introspected for C, Python, Rust, JS and Vala), on GIO alone so non-GTK apps and the Rust core can use it. `luma_sync_store_new(zone, error)` (a `GInitable`; a bad label fails at once), `put`, `get`, `remove`, `list`, `fetch_changes`, `put_asset`, `remove_asset`, `open_asset`, `lease`, `resolve_siblings`, the `changed` (a payload-free nudge) and `siblings` signals, and `status`. Every time it exposes is milliseconds since the Unix epoch, UTC (`_ms`). Without the portal (another OS, an old Luma) every call works locally and `status` says `unavailable`. A Kotlin library for the Android companion and a TypeScript one for the web companion come with those companions.

### 4. Permission

1. **One switch per app, in the ADR-052 permission store.** The row is `luma / sync`: `on`, `off` or absent. Settings › Apps › *App* and Settings › Connect › Sync show the same switch, with usage and **Delete synced data**. The switch is for the account: turning it off writes the app directory record, and every device stops syncing that app.
2. **Consent at install.** An app declares that it syncs (`sync.zones` in the Depot record; `<custom><value key="org.projectluma.sync">` in a Flatpak's metainfo). The install sheet shows "Syncs its data with your devices", and installing sets `on`. The declaration is the app's; the decision is the person's.
3. **No row yet** (installed from the command line, or an app that never declared it): the first call raises one quiet, non-blocking offer, "Let OpenLator sync its data with your devices?" with **Allow** and **Not now**. The name is the installation's (the desktop entry Flatpak exported, with the publisher's remote), never a string the app passes. Until then the app's writes stay on the device and `GetStatus` answers `offered`. "Not now" sets `off`; the switch stays in Settings. There is never a blocking prompt.
4. **Off** stops sync for that app at once. Local data stays; synced data stays until the person deletes it.

### 5. Abuse resistance

1. **Quotas** (per app per account, counted on the Hub by app tag and checked on the device first): 100 MB of records, 1 GB of resident assets, 16 zones, 100,000 records; on-demand assets in transit at most 2 GB, and relayed at most 10 GB a month. All apps together may hold at most half of the account's 10 GB, so app data can never crowd out the account's own sync. The Hub caps an account at 256 app tags. A device that lies about tags can't exceed the account's own quotas.
   - *Server capacity:* the Hub's `total_bytes` is sized by the operator to the allowances of the accounts it admits, and new data is refused with `server_full` while free space is under the reserve. One account can never hold more than its own quota.
2. **Rate limits** (in the service; the Hub's per-device limits of 600 writes and 50 MB an hour stay as they are, and system zones keep at least half of them):
   - all apps together: at most 300 Hub writes and 25 MB of uploads an hour per device, after coalescing, with bursts of 2,500 writes and 1 GB for a first sync;
   - each app: an equal share of that while several apps are busy, and at most 120 writes and 20 MB an hour, with bursts of 600 writes and 256 MB;
   - calls: 4 in flight per app on its own worker, each with a deadline; 600 calls a minute; 64 leases.
   Over a limit, writes stay in the outbox and `GetStatus` says so; reads are local.
3. **Size caps:** names 255 bytes, values 256 KiB, 100 records per call, labels `[a-z0-9][a-z0-9._-]{0,31}`, inline assets 64 MiB, on-demand assets 16 GB, an outbox of 64 MB per app, counting values and write metadata only. Queued inline asset bytes wait in the service's spool and count against the app's inline quota, not the outbox cap. Anything over is refused with a typed error before any work.
4. **No tunnel.** The API has no message, stream or socket call, no way to name a device or address, and no payload on leases or signals. Bytes leave only as the service's own encrypted records and chunks, to the person's own devices and the Hub. An app that wants a network has the network permission (ADR-054 §5b), not this.
5. **No other people.** The API has no account, user, contact or device identifiers beyond the person's own device names. Zones exist only inside the caller's account; nothing in the API reaches another account.
6. **The service stays small under attack.** Each call does bounded work; descriptors are copied with a cap and a deadline, never by path; values are opaque bytes and are never parsed; an app's mirror is a separate table space keyed by owner and app; a slow or stuck call ties up only that app's worker.
7. **Re-requests.** An on-demand asset evicted on a device can be requested again there at most 3 times a day, so one app can't spend transit or relay by evicting and fetching in a loop.

### 6. Bandwidth

1. **Records and inline assets** go through the Hub, which is what keeps devices that are never online together in sync. They are small by the caps above.
2. **On-demand assets** go device to device on the peer lane (ADR-054 §6a): LAN first, then direct, then Luma's relay within its 50 GB a month. The Hub holds them only in transit, within the account's 10 GB for 14 days, and only when no other device holds the asset and one has asked for it. Until the peer lane ships, on-demand assets sync their metadata and `OpenAsset` answers `not-here` on other devices.
3. **Reads cost nothing.** `FetchChanges`, `Get` and `List` read the local mirror. The service fetches from the Hub once per change for all apps together (the existing long-poll), however often apps ask.
4. **Metered and low-power networks.** Inline assets and on-demand downloads wait for an unmetered network unless the person pinned the item; records always go.

### 7. TVs

1. The API has no secret type. Apps keep credentials in the Secret portal, whose items sync only through `luma-keyring`, never on a TV (ADR-054 §3).
2. A zone reaches every device class by default (ADR-054 §5a.1). Limiting a zone to classes (`classes: computer, handheld`) comes in Phase 2, and then it is cryptographic: the zone key is wrapped with HPKE to each allowed device's box key instead of under the account key, and rewrapped at every rekey. The device class moves into the signed member bundle (bundle v3) first, because today it is a Hub field a hostile Hub could change. Until then the option is refused rather than half-kept.
3. On a TV, `GetStatus` reports `tv`, and a lease shows the TV's name, so a game paused on the TV says where it is.

### 8. Billing hooks

1. Every limit in section 5 comes from the account's **plan**, a Hub column that is `free` today. A plan names its resident, transit and relay allowances; the per-app limits are the same on every plan.
2. The Hub meters per account per day: resident bytes at the peak, transit bytes, relay bytes. It never meters an account by app, so a paid tier can't need to know what someone runs. Per-app analytics are separate and never linked to an account (section 10.4).
3. `quota` errors say which allowance is full, so a later paid tier can offer more where it applies. Nothing is charged to app developers.

### 9. Revocation and removal

1. **The person turns the app off:** sync stops, data stays (section 4.4).
2. **Delete synced data** (the person, in Settings) removes the app's zones from the Hub and every device's mirror and cache. It doesn't touch the app's own files.
   - `DeleteZone` from the app itself is kept for 30 days: the directory record marks the zone deleted, devices stop showing it to the app, and Settings offers **Restore** until it is removed for good. An exploited app can't wipe its data everywhere in one call. It can still delete its records one by one (`List`, then `Delete` on each current version), which removes them everywhere with no bin: the bin covers the zone, not every record, and a per-record bin would mean keeping every deleted version.
3. **The app is removed from one device:** that device drops the app's mirror, cache, outbox and leases. The zones stay for the other devices.
4. **The app is on no device:** each device lists itself in the app's directory record while the app is installed there, refreshed daily whatever the app's sync state (off, suspended, offered, no registry), and marks itself removed when the app goes (section 1.5). When every device of the account that listed the app has marked it removed, the last of them more than 30 days ago, the next device online deletes its zones; never while the person has switched the app off, Luma has suspended it, or there is no current registry. An app that merely doesn't sync is never "abandoned". Settings lists it until then as "Removed from your devices", with **Delete synced data**.
5. **A device is removed** from the account: the rekey covers app zones; the removed device drops every app mirror when it learns it was removed.
6. **Deleting all synced data** or the account removes app zones with everything else (ADR-054 §6.6).

### 10. Approval, revocation and analytics

The API is gated. An app gets sync only after Luma approves it, Luma can withdraw that at any time, and Luma sees in detail how much of Luma Sync each approved app uses. None of this needs the Hub to learn which person uses which app.

1. **Applying.** A developer registers the app in the Luma Connect developer program (`/connect/developer`, the existing program): app ID, publisher (the Flatpak remote URL and its signing-key fingerprints, from which the owner of section 1.2 is computed, or later the Depot publisher key), the zone labels it will use and what each holds, the expected size per person, and a contact. Each application is a row in the Hub's **app registry** with a state: `applied`, `declined`, `approved`, `suspended`, `revoked`. Only `approved`, `suspended` and `revoked` rows are published to devices.
2. **Approval in the Hub.** Luma staff review the application in the Hub admin (`admin.simplyluma.com`, a new *Sync apps* view): the publisher, the labels, the declared use, and a test install. Approval records who approved it and when, the exact owner (so a lookalike from another remote is not approved), the approved labels, and the app's limits (section 5's defaults, which the reviewer may lower, or raise up to the account-wide cap). Every change is kept in an audit log. Luma's own first-party apps go through the same registry, approved by the release process.
3. **The signed registry on devices.** The Hub publishes the approved set as a **signed app registry** on `dl.simplyluma.com`, signed by a Luma registry key the way the update graph is signed, with a version and an expiry. The sync service refreshes it every 6 hours, and at once when the Hub's long-poll says it changed. Each entry carries the approved publisher's public keys in full; a device decides who an app is by verifying the deployed commit's signature against those keys (section 1.2), never from the local remote configuration. An app syncs only while the current registry lists its exact (owner, app) pair as `approved`, and only for its approved labels; anything else answers `not-approved`. Removing a key from an entry stops apps signed by it at the next refresh. The format and URLs are in `docs/operations/connect-sync-apps-hub.md`. Without a valid registry (offline past its expiry), apps keep working locally and their writes wait in the outbox, as with Sync off. Nothing about who uses an app goes to the Hub to check approval: every device reads the same public list.
4. **Revocation.** Moving an app to `suspended` or `revoked` in the Hub admin publishes a new registry. Within one refresh (at most 6 hours, usually seconds through the long-poll hint), every device stops sending and fetching that app's zones, drops its outbox, and answers `suspended` ("Paused by Luma" in Settings) or `revoked` ("Stopped by Luma"); writes from then on are `local`: kept on that device as local-only versions that record the version they were written over. Suspending keeps the data, and sync resumes by itself when a later registry approves the app again (a new approval after a revoke does the same): the service then offers every local-only version through the outbox, keep-both against its recorded base, within the outbox cap and the quotas, and `Changed` reports each outcome; the app does nothing. Revoking also marks the app *purge*: each device deletes the app's zones from the Hub and its own mirror of synced versions through the app directory (section 1.5), but only after two verified registries, of different versions signed at least 12 hours apart, both list the purge, and the device's own clock shows at least 12 hours since it first saw the purge listed (a registry signed more than 5 minutes in the device's future counts for neither), so one bad or compromised signing, or a key that signs two registries a minute apart, can't delete everyone's data at once; until then the app is only stopped. Local-only versions written on a device while the app was stopped are the person's data on that device and are never purged. The Hub can't find an app's zones by itself, by design. The person sees "Luma stopped sync for this app" in Settings with **Delete synced data**. Revocation is per app, never per person.
5. **Analytics.** Daily per-app reports are **off by default**. Two switches must both be on: the device's `apps.reports` (a root-owned config file Luma ships; it ships none) and the Hub's `config.sync.apps.reports`, which answers `{"collecting": false}` while off. They stay off until the reports' aggregation no longer has to trust the Hub operator: DAP/Prio with a second, independent aggregator, behind OHTTP. Sync ships without per-app reports until then. When reports are on, this is what goes out and what it does and doesn't protect.
   - *Presence says nothing about use.* Each UTC day, a device sends one report for every approved app installed on it with sync switched on, whether or not the app ran that day.
   - *No count goes out as it is.* The Hub sees every app zone's tag, padded sizes, counts, times and writing device (section 2.5). Usage, conflicts, refusals, errors, and the read calls that follow the Hub's change signals all echo what it serves a device and a tag. So a report carries exactly one of 17 such quantities, as a log-4 bucket (values below 1 are bucket 0) through two layers of randomized response:
     - The quantity and its true bucket are fixed per app at the first report of each UTC month.
     - A permanent response is drawn once per (app, quantity, bucket) with ε = 2 and kept for good (RAPPOR-style memoization), so a value reported again costs nothing.
     - Each report re-randomizes the kept response with ε = 4, so one device's reports don't repeat a fixed value.
   - *What that guarantees, and no more.* Suppose the Hub knows every true value for a tag and can link all of one device's reports for one app. Those reports then reveal at most ε = 2 per distinct (quantity, bucket) drawn: at most 2 per month per app, and nothing more once the values repeat. A device's reports for several apps compose.
   - *Not randomized:* the app, the day and the context (device class, CPU architecture, the app's version, and the Luma release coarsened to its base and week). With the IP address and timing, these can let the Hub operator link a small app's reports to one device and so to an account. Randomized response doesn't prevent that linking; it only bounds what the numbers add. This is why reports are off.
   - *Analytics are estimates.* The Hub recovers distributions per app, day and cell with an unbiased estimator, good over hundreds of reports, useless for small apps.

   Reports carry no account, device or zone identifier. Each one is authorised with a single-use **anonymous token** (publicly verifiable RSA blind signatures, RFC 9474 and RFC 9578, type 0x0002), and the Hub can't link a redeemed token to the device it was issued to.
   - *Issuance:* a device gets its day's tokens while it authenticates for sync, always exactly 64 whatever it needs, so the count says nothing.
   - *One key per month:* token keys follow a fixed public calendar, one key per UTC month, published at least 7 days ahead and never changed. A device uses only the current month's key; with none, or a different one than it first saw for that month, it sends nothing. A Hub serving one device a stale registry or a key of its own can silence that device but can't make its reports stand out.
   - *Sending:* each report goes at its own random time on a fresh connection, never with a sync request; overdue reports are spread over the next day rather than sent in a burst.
   - *What the Hub keeps:* only per-app aggregates per day and cell: per-field bucket counts and the count of reports, which is the number of devices with the app installed and syncable, not active ones. No report rows.
   - *IP addresses:* unlinkability from the device's address rests on the Hub not logging addresses on the metrics endpoint. That is policy, not cryptography, until reports go through a third-party relay.

   The wire contract is `docs/operations/connect-sync-apps-hub.md`.
6. **Who sees what.** Luma staff see every app in the Hub admin: state, limits, devices with the app installed and device-days over a range (there is no monthly distinct count), estimated distributions of resident storage, transfer, writes, sync latency, conflicts, errors and limit hits, broken down by device class, architecture and version over any date range, with exports. The developer sees the same views for their own app only, in the developer program. Any breakdown cell covering fewer than 10 devices is merged into "other", with complementary suppression, so no small group is singled out or recovered by subtraction. The person sees their own per-app usage in Settings, computed on the device, never from the Hub.
7. **Enforcement stays where it is.** Quotas and rate limits are still enforced on the device and on the Hub by app tag (section 5). Analytics only observe, and an app over its limits shows in both views.

## Alternatives rejected

- **A sync service apps talk to directly** (`org.projectluma.ConnectSync1`). A Flatpak would need `--talk-name`, which every app would request, and the service would have to name callers itself. The portal already names callers for every other portal.
- **A REST API with per-app tokens**, CloudKit-style. Apps would hold credentials and talk to the Hub, which then learns which app is which and has to carry every app's request rate.
- **App-held keys** (the app encrypts its own records). A compromised app leaks its key and the service can't enforce quotas or keep-both on content it can't see. The service seeing plaintext is no loss: it is the person's own device.
- **Generic peer-to-peer tunnels between an app's instances.** Small to build and the most efficient, but it is a network tunnel for untrusted code, is useless when the two devices are never online together, and its traffic can't be capped by content.
- **Letting the Hub know app IDs** (ADR-054 §1.8). Per-account tags give the quotas without telling Luma what someone runs.
- **Cryptographic exclusion of TVs from chosen zones.** It needs a second account key that TVs don't hold and a second rekey path; a TV is a member, so the real line is that secrets go to the keychain.
- **Automerge documents in Phase 1.** Records with keep-both cover saves, libraries, recipes and settings. `Document` comes when an adopter needs merging text.

## Tradeoffs

- The service sees each app's plaintext. It runs as the person, on their device, and already holds every key.
- An app can fill its own quota with junk and lose its own sync. It can't affect another app beyond the account's shared 10 GB, which Settings shows per app.
- Writes from a device with a wrong clock can win keep-both ordering; the hybrid logical clock bounds this and the other version is kept, not lost.
- Bundles without a signing key don't sync. That is the price of an identity no one can claim.
- Leases are advisory: two devices can play the same save at once, and the result is two versions, not a merge.
- The TV class limit is a policy, not cryptography (section 7).
- On-demand assets wait for the peer lane; until then only their metadata syncs.
- Apps see the names the person gave their devices, so "from Living room TV" can be shown. An app could already read the hostname.
- An app with write access to the home folder can rewrite a user Flatpak installation, and so claim another app's owner. It could already read that app's folder; the protection is the sandbox level, which Settings and Depot show.
- Padding and coalescing hide record sizes and write timing only roughly. The Hub can still see that an app tag exists and is active.
